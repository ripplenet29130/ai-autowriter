# 記事品質改善（Cプラン）仕様書

作成日: 2026-11-06
更新日: 2026-11-09（実装を反映）
ステータス: 実装済み・デプロイ前（実際の API での確認待ち）

## 1. 目的

AI記事の「質」と「事実の正確さ」を上げる。
具体的には、次の3点を実現する。

1. 書く前に Google 検索で根拠を集め、根拠に基づいて書かせる
2. 本文の執筆と見直しを上位モデル（Gemini 3.1 Pro）で行う
3. ファクトチェックを Gemini の検索機能で行い、誤りのある記事が公開されないようにする

## 2. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | Gemini の API キー | 当面は**無料キー**を使う。3.1 Pro は無料枠がないため、Pro が使えないときは**自動で 3.8 Flash に代替**する。有料化したら設定変更なしで Pro が使われる |
| 2 | Supabase のプラン | 当面は**無料プラン（実行時間の上限 150 秒）**。有料化（上限 400 秒）も想定し、時間の上限を設定で変えられるようにする |
| 3 | Perplexity | **廃止**。ファクトチェックは Gemini の検索だけで行い、Perplexity の設定項目は画面から外す |
| 4 | 参考資料 | **オン**（既定オン。スケジュールごとにオフにもできる） |
| 5 | 対象範囲 | **自動投稿（スケジューラー）と手動生成画面の両方** |

### 無料キーで動かす間の注意

- 有料化までは、本文の執筆と見直しも 3.8 Flash で行われる（実質 B プランの動き）。有料キーに替えた時点で C プランになる。
- 無料キーでは、Google が入力内容をサービス改善に使う場合がある。お客様の機密情報を含む指示は入れない。
- 無料キーでは 1 分あたりの回数に上限がある。上限に当たったら待って再試行する（5.10）。
- 無料キーで Google 検索が使えるかは実装時に実際に呼び出して確認する。→ 2026-11-09 に確認し、**使えなかった**（12 章）。使えない場合は検索なしで動き、通知・画面で知らせる（その場合、根拠メモとファクトチェックの精度は下がる）。

## 4. 現状と課題

| 項目 | 現状 | 課題 |
|---|---|---|
| 本文の根拠 | AI が覚えている知識だけで書いている | 古い情報や作り話（もっともらしい誤り）が混ざる |
| 競合調査 | SerpAPI で上位記事の見出しを取得 | 見出ししか使っておらず、事実情報は渡していない |
| 使用モデル | 全工程で同じモデル（既定は `gemini-3.5-flash`） | `gemini-3.5-flash` は Google の料金表から消えており、提供終了の可能性がある |
| 見直し | 処理の枠はあるが中身は空（何もしていない） | 重複・根拠のない断定・つながりの悪さが残る |
| ファクトチェック | 数字・日付を含む文を機械的に抽出し、Perplexity で確認 | 抽出が粗い。Perplexity の契約が別途必要 |
| 自動修正 | 直せない場合「（修正: …）」「【AI修正サマリー】」を本文に挿入 | その文言が入ったまま公開される可能性がある |
| ファクトチェック失敗時 | 警告を出すだけで、設定どおり公開される | 確認できていない記事が公開される |
| 費用記録 | 文字数から推定 | 実際のトークン数と検索回数が記録されていない |

## 5. 共通の仕組み（自動投稿・手動生成の両方で使う）

### 5.1 モデルの使い分け

- **基本モデル**: `gemini-3.8-flash`（根拠メモ、タイトル、構成案、ファクトチェック、自動修正）
- **執筆モデル**: `gemini-3.1-pro-preview`（本文の執筆、編集見直し）
- **品質モード**を追加する。
  - `high`（高品質＝Cプラン）: 上記のとおり。**既定値**
  - `standard`（標準＝Bプラン）: 執筆・見直しも基本モデルで行う
- スケジュールや画面でモデルを個別に指定している場合は、その指定を基本モデルとして使う。
- **Pro の自動代替**: Pro の呼び出しが 403（権限なし）/ 429（無料枠・上限超過）/ 404（モデルなし）で失敗したら、基本モデルで書き直す。1 回の実行の中で一度失敗したら、それ以降は Pro を呼ばない（無駄な待ち時間を防ぐ）。代替したことは通知・画面に出す。
- 既定モデルを `gemini-3.5-flash` から `gemini-3.8-flash` に変更する。保存済みの `gemini-3.5-flash` は読み込み時に 3.8 Flash に読み替える（`aiModelCatalog.ts` の置き換え表に追加。DB 書き換えは不要）。
- モデル ID は実装時に Gemini API のモデル一覧で実在を確認する。
- Pro の思考（thinking）の上限は、執筆 1,024 トークン、見直し 2,048 トークンとする（今は 128）。

### 5.2 根拠メモ（新規）

**目的**: 本文に使ってよい事実を、出典付きで先にそろえる。

- **入力**: キーワード、タイトル（決まっていれば）、競合記事の見出し、関連キーワード
- **呼び出し**: 3.8 Flash ＋ Google 検索（`tools: [{ google_search: {} }]`）
  - 1 回目: テーマの基本情報（定義・仕組み・数字・制度）
  - 2 回目: 最新情報（直近の改定・価格・統計の最新値）。時間が足りない場合や 1 回目で十分な場合は省略
- **出力（JSON）**:
  - `facts`: 事実の一覧（最大 25 件）。各項目に「内容」「数値」「いつ時点か」「出典番号」を持つ
  - `sources`: 出典の一覧（タイトル、URL）
  - `cautions`: 情報が割れている点・変わりやすい点
- **出典 URL の扱い**: 検索結果の URL は Google の転送用 URL になっているため、転送先（元の URL）を取得して保存する（1 件 5 秒まで、並列で取得）。取得できなかった出典は参考資料に使わない。
- **失敗時**: 根拠メモなしで今までどおり生成を続け、通知・画面で知らせる。

### 5.3 構成案・本文の執筆ルール

構成案では、見出しごとに使う根拠の番号を割り当てる。本文の指示に次を追加する。

- 数字・日付・料金・制度名・法令名・統計は、**根拠メモにあるものだけ**使う
- 根拠メモにない具体的な数字は書かない。必要なら「一般的には」「目安として」のように断定を避ける
- 変わりやすい情報（料金・制度・統計）には時点を書く（例: 「2026年11月時点」）
- 根拠メモの `cautions` にある点は、断定しない書き方にする
- 見出しごとに、その見出しに割り当てた根拠だけを渡す（関係ない情報を渡さない）

### 5.4 編集見直し（新規）

- 執筆モデルに記事全体と根拠メモを渡し、修正後の記事全文を返させる。
- 見直す点:
  - 同じ内容の繰り返し
  - 根拠メモにない断定
  - 見出しと本文のずれ
  - セクション間のつながり
  - 読者の疑問に答えているか（結論が先に書かれているか）
- 守らせる点: 見出しの数と順番を変えない、文字数を ±15% 以内に保つ、新しい事実を足さない
- **採用条件**: 見出し数が変わった／文字数が ±15% を超えた／空の見出しがある場合は、見直し結果を捨てて見直し前の記事を使う。

### 5.5 ファクトチェック（作り直し）

1. **主張の抽出**（3.8 Flash、検索なし）
   AI に「確認が必要な主張」を最大 20 件抜き出させる。種類（数値・日付・制度・固有名詞・比較）を付ける。
   手動で `[[ ]]` で囲んだ箇所は今までどおり必ず対象にする。
   AI の抽出に失敗したら、今の機械的な抽出に切り替える。
2. **根拠メモとの照合**（3.8 Flash、検索なし）
   各主張を「根拠メモと一致」「根拠メモと矛盾」「根拠メモにない」に分ける。「一致」はここで確認済み（`correct`）とする。
3. **検索での確認**（3.8 Flash ＋ Google 検索）
   「矛盾」と「根拠メモにない」主張だけを、5 件ずつ検索で確認する（無料キーでは 1 件ずつ順番に、有料キーでは 2 並列）。
4. **判定の形式**: 結果は今と同じ形式（`correct` / `incorrect` / `partially_correct` / `unverified`、確信度、出典 URL、説明）で保存する。画面と DB はそのまま使える。
5. **自動修正**: 3.8 Flash で行う（今は Perplexity）。修正後は、**修正した主張だけ**を再確認する（今は記事全体をもう一度確認している）。
6. **Perplexity の廃止**: Perplexity を呼ぶ処理と設定画面の項目を外す。登録済みの Perplexity キーは DB に残すが使わない。
7. **実行条件**: ファクトチェック設定がオンで、Gemini キーがあれば実行する（Perplexity キーは不要になる）。

### 5.6 公開判定

今の条件（重大な指摘が残ったら下書き）に、次を追加する。

| 条件 | 対応 |
|---|---|
| 重大な指摘（誤り・確信度 70% 以上）が残った | 下書きにする（今と同じ） |
| 本文に「（修正: 」「【AI修正サマリー】」が残っている | 下書きにする |
| ファクトチェック自体が失敗した、または時間切れで省略した | 下書きにする（今は公開されてしまう） |
| 「確認できなかった」主張が 5 件以上ある | 公開はするが通知で警告する |

手動生成画面では投稿操作を人が行うため、下書きを強制せず、投稿ボタンの近くに警告を表示する（7 章）。

### 5.7 参考資料の付記（新規）

- 記事末に「## 参考資料」を追加し、本文で実際に使った根拠の出典を最大 5 件、リンク付きで載せる。
- 公的機関（`go.jp`、`lg.jp` など）の出典を優先して並べる。
- 既定はオン。自動投稿はスケジュールごと、手動生成は画面でオフにできる。
- 出典 URL を 1 件も取得できなかった場合は、この見出しごと付けない。
- 文字数の調整（`compactArticleToTargetLength`）と見出し数の検査の対象から、参考資料は外す。

### 5.8 費用記録

- Gemini の応答に含まれる実際のトークン数（入力・出力・思考）を、モデルごとに合計して記録する（今は文字数からの推定）。
- Google 検索の回数を記録する。費用は「月 5,000 回の無料枠を超えた場合」の単価（$14 / 1,000 回）で計算する。
- 無料キーで動いている間も、有料だった場合の金額として記録する（有料化の判断材料にする）。
- 単価表を更新する。

| モデル | 入力（$ / 100万トークン） | 出力（$ / 100万トークン、思考を含む） |
|---|---|---|
| 3.8 Flash（〜2026/12/31） | 0.75 | 3.75 |
| 3.8 Flash（2027/1/1〜） | 1.50 | 7.50 |
| 3.1 Pro | 2.00 | 12.00 |

### 5.9 Gemini 呼び出しの共通部品

自動投稿（`scheduler-executor`）と手動生成（ブラウザ → `ai-proxy`）の両方で、次の機能を持つ呼び出しを用意する。

- モデルを工程ごとに指定できる
- Google 検索を付けて呼び出せる（応答から出典一覧を取り出す）
- 応答のトークン数（入力・出力・思考）を返す
- 思考の上限を指定できる
- JSON 形式での応答を指定できる

`ai-proxy` には `gemini` の呼び出しに上記の指定を受け付ける項目を追加する（既存の呼び出し方は変えない）。出典 URL の転送先取得も `ai-proxy` 側で行う（ブラウザからは他サイトの転送先を取得できないため）。

### 5.10 回数制限（429）への対応

- 429 が返ったら、応答にある待ち時間（`retryDelay`）だけ待って再試行する。待ち時間がなければ 2 秒・4 秒・8 秒と延ばして最大 3 回。
- 自動投稿では、待ち時間が残り時間を超える場合は再試行せず、その工程を省略する。
- Pro の 429 は待たずに Flash に代替する（5.1）。

## 6. 自動投稿（スケジューラー）の仕様

### 6.1 処理の流れ

| # | 工程 | モデル | Google 検索 | 変更 |
|---|---|---|---|---|
| 1 | キーワード・タイトル選択 | — | — | 変更なし |
| 2 | 競合調査（SerpAPI）と**根拠メモ作成** | 3.8 Flash | あり | 根拠メモを**新規**追加。競合調査と同時に実行 |
| 3 | タイトル生成 | 3.8 Flash | なし | 根拠メモの要約を渡す |
| 4 | 構成案（アウトライン） | 3.8 Flash | なし | 根拠メモを渡し、見出しごとに根拠を割り当てる |
| 5 | **本文執筆** | **3.1 Pro**（代替: Flash） | なし | 見出しごとに関係する根拠だけ渡す。H2 単位で並列 |
| 6 | **編集見直し** | **3.1 Pro**（代替: Flash） | なし | **新規**（今は空の処理） |
| 7 | **ファクトチェック** | 3.8 Flash | 必要な分だけ | **作り直し** |
| 8 | 自動修正 | 3.8 Flash | なし | Perplexity から Gemini に変更 |
| 9 | 公開判定 | — | — | 判定条件を追加 |
| 10 | **参考資料の付記** | — | — | **新規** |
| 11 | WordPress 投稿・通知・費用記録 | — | — | 記録・通知の項目を追加 |

### 6.2 本文の並列執筆

- 本文は **H2 単位で並列に書く**（H2 の中の H3 は順番に書く）。並列数は有料キーで最大 4、無料キーで 2。
- 並列にすると前のセクションの続きを参照できなくなるため、つながりは編集見直しで整える。見直しを時間切れで省略した場合は、今と同じ順番の執筆に戻すかを経過時間で判断する（残り時間に余裕があれば順番、なければ並列）。

### 6.3 処理時間の管理（無料プラン 150 秒対策）

- 実行時間の上限を環境変数 `SCHEDULER_TIME_BUDGET_SECONDS` で設定する。既定は **140 秒**（無料プランの 150 秒から余裕を取る）。Supabase を有料化したら **380 秒** に変更する。
- 経過時間は、その実行（Edge Function の呼び出し）の開始から数える。同じ時刻に複数のスケジュールが動くと、後のスケジュールほど使える時間が減るため、**スケジュールの実行時刻は 1 件ずつずらす**ことを推奨する。
- 工程ごとに、始める前に残り時間を確認し、足りなければ省略する。

| 工程 | 実行に必要な残り時間 | 足りない場合 |
|---|---|---|
| 根拠メモ 2 回目 | 110 秒以上 | 1 回目だけにする |
| 根拠メモ 1 回目 | — （最大 25 秒で打ち切り） | 根拠メモなしで続ける |
| 編集見直し | 80 秒以上 | 省略する |
| ファクトチェックの検索確認 | 45 秒以上 | 根拠メモとの照合だけ行い、**下書き保存** |
| 自動修正後の再確認 | 30 秒以上 | 省略し、**下書き保存** |
| WordPress 投稿 | 15 秒は常に確保 | — |

- 省略した工程は通知に出す。

**無料プラン・無料キーでの処理時間の見込み**（Pro は使えず Flash で代替される前提）

| 工程 | 見込み |
|---|---|
| 競合調査＋根拠メモ（同時実行） | 20〜25 秒 |
| タイトル・構成案 | 15〜20 秒 |
| 本文（Flash、2 並列） | 25〜35 秒 |
| 見直し（Flash） | 15〜20 秒 |
| ファクトチェック・修正 | 30〜50 秒 |
| 投稿・通知 | 5〜10 秒 |
| **合計** | **約 110〜160 秒** |

上限 140 秒を超えそうな場合は、上の表のとおり見直しや再確認が省略される。Supabase を有料化すると、すべての工程を省略なしで実行できる（Pro 使用時の見込み 約 140〜220 秒）。

### 6.4 Chatwork 通知

ファクトチェック通知に次の項目を追加する。

- 根拠メモの件数・出典数
- Google 検索の回数
- 執筆に使ったモデル（Pro が使えず Flash で代替した場合はその旨）
- 見直しの結果（採用／不採用／時間切れで省略）
- 時間切れで省略した工程
- 推定費用（円換算、$1＝150円）

### 6.5 記録

- 根拠メモ、トークン数、検索回数、省略した工程は、実行履歴の `cost_breakdown`（既存の JSON 列）に保存する。テーブルは追加しない。

## 7. 手動生成画面の仕様

手動生成はブラウザから工程ごとに `ai-proxy` を呼ぶため、150 秒の上限は 1 回の呼び出しごとにかかる（全体の時間制限はない）。そのため手動生成では工程を省略せず、すべて実行する。

### 7.1 段階的に作る画面（MultiStepGenerator）

| ステップ | 今 | 変更後 |
|---|---|---|
| 1. 競合・トレンド分析 | 競合記事・関連キーワードを表示 | **根拠メモを作成して表示**。事実ごとに出典リンクを付け、使わない事実のチェックを外せる |
| 2. タイトル選択 | 変更なし | 根拠メモの要約を渡す |
| 3. 構成案の編集 | 変更なし | 根拠メモを渡し、見出しごとに根拠を割り当てる |
| 4. 本文生成 | 見出しごとに順番に生成 | 執筆モデル（Pro、代替 Flash）で、見出しごとに根拠を渡して生成。生成後に**編集見直し**を自動で行い、見直し前後の差分を確認できる |
| ファクトチェック | Perplexity で確認 | Gemini 方式（5.5）で確認。結果の表示は今の画面を使う |
| 投稿 | — | 重大な指摘が残っている／修正文言が残っている場合、投稿ボタンの近くに警告を出す |

- 手動生成では本文を見出しごとに順番に書く（時間制限がないため並列にしない。つながりが自然になる）。
- 根拠メモの作成に失敗した場合は、ステップ 1 に「根拠メモを作成できませんでした」と出し、再作成ボタンを置く。

### 7.2 自動モード（AIGenerator の一括生成）

- 段階的な画面と同じ処理を、画面操作なしで順番に実行する。
- 進行状況の表示に「根拠メモ作成中」「見直し中」「ファクトチェック中」を追加する。

### 7.3 画面の設定項目

- 記事生成画面に「品質モード（高品質／標準）」と「参考資料を付ける」を追加する（既定: 高品質・オン）。
- Pro が使えず Flash で代替した場合は、生成後に「有料キーでないため Flash で執筆しました」と表示する。

## 8. DB・画面の変更

### DB（マイグレーション 1 本）

| テーブル | 列 | 型・既定値 | 用途 |

## 10. 費用の目安（画像なし）

前提: 2,000 字の記事、2027 年以降の料金、$1＝150 円。

| 月の記事数 | 無料キーの間 | 有料キー・Cプラン |
|---|---|---|
| 50 本 | 0 円（回数制限の範囲内） | 約 5,100 円 |
| 100 本 | 0 円（回数制限の範囲内） | 約 1.0 万円 |
| 300 本 | 回数制限に当たる可能性あり | 約 3.1〜3.9 万円 |

- 有料キー・C プランは 1 記事あたり約 100 円。
- 月 100 本以下なら、Google 検索は月 5,000 回の無料枠に収まる。
- 2026 年 12 月末までは 3.8 Flash が半額のため、実際はこれより安くなる。
- Supabase の有料化は別途費用がかかる（本書の対象外）。

### 仕様との違い・追加した判断

- **検索なしで作られた根拠メモは使わない**: Google 検索が使われなかったメモは AI の知識だけなので、本文の根拠にもファクトチェックの照合にも使わない（照合で「正しい」と誤判定しないため）。
- **Gemini キーが見つからない場合**: 自動投稿ではファクトチェックを実行できないため下書きにする。
- **タイトル生成**: 根拠メモの要約は渡していない（根拠メモはタイトル生成と同時に作るため）。自動投稿の根拠メモは、競合調査と同時に作るので、キーワードと決まっているタイトルだけを使う。
- **並列数**: 6.2 の「見直しを省略したら順番の執筆に戻す」判断は入れていない。並列数は `GEMINI_MAX_PARALLEL` で固定。
- **手動生成のファクトチェック**: 検索確認は 1 件ずつ順番に行う（無料キーの回数制限に当たりにくくするため）。
- **旧 Perplexity 設定**: ファクトチェック設定画面を開くと、ブラウザに保存されていた旧設定（Perplexity キーを含む）を削除する。DB の Perplexity キーは残すが使わない。
- **参考資料のリンク**: 自動投稿・レビュー画面からの投稿・手動投稿の 3 経路で、Markdown のリンクを HTML のリンクに変換するようにした。
