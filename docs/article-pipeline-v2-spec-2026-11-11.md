# 記事作成の新方式（v2）仕様書

作成日: 2026-11-09
ステータス: たたき台（実装前）
更新日: 2026-11-09（検証 AI を ChatGPT に決定、画面は管理者のみ）

## 1. 目的

記事作成の仕組みを根本から作り直す。調査（検索）・執筆・検証まで、すべて AI の API で行う。

1. 検索は AI の検索機能だけで行う（SerpAPI・Google Custom Search を使わない）
2. 書く AI と確かめる AI を別の会社にして、誤りの見逃しを減らす
3. 工程ごとに分けて実行し、時間切れで工程を省略しない
4. 自動投稿と手動生成で同じ仕組みを使う

まずは**テスト**として、今の仕組みと並べて動かす。

## 2. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | 今の仕組み | **変更しない**。今の自動投稿・手動生成はそのまま動き続ける（3 章） |
| 2 | 調査・執筆の AI | Gemini（Google 検索・ページ読み込み機能を使う） |
| 3 | 検証の AI | **ChatGPT（OpenAI）**。アプリで設定済みのキーを使う。Web 検索機能で自分でも確かめる |
| 4 | SerpAPI | 新方式では**使わない**。今の仕組みでは使い続ける |
| 5 | 実行の仕組み | 工程ごとに分けて実行し、途中経過を DB に保存する（5 章） |
| 6 | テスト期間中の投稿 | **常に下書き**で投稿する |

## 3. 今の仕組みを崩さないための方針

- 新方式は**新しい部品だけ**で作る。

| 種類 | 新方式で使うもの | 今の仕組みへの影響 |
|---|---|---|
| Edge Function | 新規 `article-pipeline` | なし（`scheduler-executor`・`ai-proxy` は触らない） |
| DB | 新規テーブル `article_jobs`・`article_job_steps` | なし（既存テーブルは変更しない） |
| 画面 | 新規ページ「新方式（テスト）」 | メニューに 1 項目足すだけ |
| 共通部品 | `src/shared/` は**読み込んで使うだけ**。手を加える必要があるときは新しいファイルを作る | なし |
| 定期実行 | 新しい定期実行（毎分）を 1 件追加 | なし（既存の `article-scheduler-check` は触らない） |
| WordPress 投稿 | 既存の投稿用 Edge Function を呼ぶ | なし |

- 新方式を止めたいときは、新しい定期実行を止めてメニューを隠すだけで元の状態に戻る。
- 「新方式（テスト）」の画面は、テスト期間中は**管理者だけ**に表示する。お客様のアカウントには出さない。
- 今の未コミットの変更（Cプラン）は、新方式の作業を始める前にコミットしておく（何が「今の仕組み」かをはっきりさせるため）。

## 4. 処理の流れ

| # | 工程 | AI | 検索 | 内容 |
|---|---|---|---|---|
| 1 | 検索意図・競合調査 | Gemini | Google 検索＋ページ読み込み | 上位に出るページを AI に読ませ、検索意図・見出し構成・読者の疑問・関連キーワードをまとめる |
| 2 | 根拠集め | Gemini | Google 検索 | 本文に使える事実を出典付きで集める（定義・数字・制度・最新情報）。出典 URL は元の URL に直して保存 |
| 3 | 企画 | Gemini | なし | タイトル候補を作って 1 つ選び、構成案を作る。見出しごとに使う根拠を割り当てる |
| 4 | 執筆 | Gemini（上位モデル） | なし | H2 ごとに順番に書く。前のセクションを参照できるのでつながりが自然になる |
| 5 | 見直し | Gemini（上位モデル） | なし | 重複・根拠のない断定・つながりを直す（Cプランの採用条件を使う） |
| 6 | 検証 | **ChatGPT** | Web 検索 | 主張を抜き出し、根拠と照合し、足りない分や重要な数字は自分で検索して確かめる |
| 7 | 修正 | Gemini | なし | 検証で誤りとされた箇所だけ直す |
| 8 | 再検証 | **ChatGPT** | 必要な分だけ | 直した主張だけを確かめる。修正と再検証は最大 2 回まで |
| 9 | 判定・投稿 | — | — | 公開判定（8 章）、参考資料の付記、WordPress へ下書き投稿、通知 |

### 検索を AI に任せることの注意

- AI の検索は Google の順位どおりの一覧を返さない。「上位記事の見出し」は AI が読んだページから取るため、SerpAPI の結果と完全には一致しない。
- テスト期間中に、同じキーワードで今の方式と新方式の調査結果を比べて、実用上の差を確かめる（11 章）。

## 5. 実行の仕組み（工程ごとの実行）

- 記事 1 本の作成を**ジョブ**と呼ぶ。ジョブは 4 章の工程を 1 つずつ進める。
- `article-pipeline` は呼ばれるたびに、**進められるジョブの次の 1 工程だけ**を実行し、結果を DB に保存する。
- 1 工程は 120 秒以内に終わるようにする（Supabase 無料プランの上限 150 秒に収める）。執筆は H2 1 つを 1 工程とする。
- 工程が終わったら、すぐに自分自身を呼び直して次の工程に進む。呼び直しに失敗しても、毎分の定期実行が拾って進める。
- 同じジョブを 2 か所で同時に進めないよう、実行中の工程には「ロック期限」を付ける。期限を過ぎたら別の呼び出しがやり直せる。
- 工程が失敗したら最大 3 回やり直す。429（回数制限）は応答の待ち時間に従う。3 回失敗したらジョブを「失敗」にして通知する。
- 失敗したジョブは、画面から**失敗した工程から**やり直せる。

### 時間の見込み

記事 1 本あたり 3〜6 分程度を見込む（工程の合計時間＋工程間の待ち）。150 秒の制限がなくなるので、どの工程も省略しない。

## 6. AI の呼び出し

| 用途 | 会社 | モデル（実装時に実在と料金を確認） |
|---|---|---|
| 調査・根拠集め・企画・修正 | Gemini | `gemini-3.8-flash` |
| 執筆・見直し | Gemini | `gemini-3.1-pro-preview`（使えなければ Flash で代替。Cプランと同じ） |
| 検証・再検証 | OpenAI | AI 設定で選んでいるモデル（既定 `gpt-5.4`）。Web 検索ツール付き |

- API キーは既存の AI 設定（`ai_configs`）から会社ごとに取る。なければ Edge Function の環境変数を使う。
- OpenAI のキーがない場合は、検証を Gemini で行い、「同じ会社の AI で検証した」ことを画面と通知に出す。
- OpenAI の Web 検索は Responses API（`/v1/responses` の `web_search` ツール）で使う。今の `ai-proxy` は別の呼び方（Chat Completions）なので、新方式用に新しく作る。
- OpenAI の回数制限（429）も Gemini と同じく待ち時間に従ってやり直す。
- 呼び出しの共通部品（モデル指定・検索・JSON・トークン数・429 対応）は Cプランの `geminiCore.ts` を使う。OpenAI 用は `article-pipeline` の中に新しく作る。

## 7. 検証の詳しい流れ

1. **主張の抜き出し**: 確かめるべき主張（数字・日付・制度・固有名詞・比較）を最大 20 件抜き出す
2. **根拠との照合**: 各主張を「根拠と一致」「根拠と矛盾」「根拠にない」に分ける
3. **自分で検索して確認**: 「矛盾」「根拠にない」に加え、「一致」でも**数字・料金・法令**に関わる主張は ChatGPT が自分で検索して確かめる（Gemini の根拠集めの誤りも拾うため）
4. **判定**: `correct` / `incorrect` / `partially_correct` / `unverified`、確信度、出典 URL、説明（今の形式と同じ）
5. **総合評価**: 記事全体について「公開してよいか」を 3 段階（問題なし・要確認・公開不可）で答える

## 8. 公開判定

テスト期間中は常に下書きで投稿する。そのうえで、本番運用に切り替えたときの判定を記録しておく。

| 条件 | 判定 |
|---|---|
| 誤り（確信度 70% 以上）が残った | 下書き |
| 本文に修正用の文言（「（修正: 」など）が残っている | 下書き |
| 検証が失敗した | 下書き |
| 検証 AI の総合評価が「公開不可」 | 下書き |
| 「確認できなかった」主張が 5 件以上 | 公開するが通知で警告 |

## 9. DB

### `article_jobs`（記事 1 本）

| 列 | 内容 |
|---|---|
| `id`, `account_id`, `user_id` | 識別子（権限は今のテーブルと同じくアカウント単位） |
| `keyword`, `settings` | キーワードと設定（文字数・トーン・WordPress 設定の ID・使う AI など） |
| `status` | 待機中・実行中・完了・失敗・キャンセル |
| `current_step` | 今の工程 |
| `title`, `content` | 完成した記事 |
| `verdict` | 公開判定の結果 |
| `wordpress_post_id`, `wordpress_url` | 投稿先 |
| `cost` | 費用（AI・モデルごとのトークン数、検索回数、円換算） |
| `locked_until`, `error` | ロック期限、エラー内容 |
| `created_at`, `updated_at` | |

### `article_job_steps`（工程 1 つ）

| 列 | 内容 |
|---|---|
| `job_id`, `step`, `attempt` | どのジョブのどの工程か、何回目か |
| `status` | 実行中・完了・失敗 |
| `output` | 工程の結果（調査結果・根拠・構成案・各セクション本文・検証結果など） |
| `provider`, `model`, `tokens`, `search_count` | 使った AI と量 |
| `started_at`, `finished_at`, `error` | |

## 10. 画面「新方式（テスト）」

- キーワードと設定（文字数・トーン・投稿先）を入れて「作成開始」を押す。作成は自動で最後まで進む。
- ジョブ一覧: 状態、今の工程、経過時間、費用
- ジョブの詳細: 工程ごとの結果を順に見られる
  - 調査結果（検索意図・競合の見出し・関連キーワード）
  - 根拠（出典リンク付き）
  - 構成案と本文
  - 見直し前後の差分
  - 検証結果（主張ごとの判定と出典）、検証 AI の総合評価
- 操作: 失敗した工程からやり直す、キャンセル、WordPress に下書き投稿（自動投稿されなかった場合）

## 11. 段階的な進め方

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| 1 | 土台（テーブル・工程の実行の仕組み・画面）と、調査〜見直しまで | 画面からキーワードを入れて本文ができる |
| 2 | 検証・修正・再検証、判定、下書き投稿、通知 | 下書きが WordPress に届き、検証結果が画面で見られる |
| 3 | 比較テスト: 同じキーワード 5〜10 本で今の方式と比べる（質・正確さ・費用・時間） | 比較結果を本書に追記 |
| 4 | スケジュール設定で「新方式」を選べるようにする（既定は今の方式のまま） | 選んだスケジュールだけ新方式で動く |
| 5 | 置き換えの判断（今の方式と SerpAPI の廃止） | 判断を本書に追記 |

段階 4 までは今の仕組みに手を入れない。段階 4 で初めてスケジュール設定に列（使う方式）を 1 つ足す。
